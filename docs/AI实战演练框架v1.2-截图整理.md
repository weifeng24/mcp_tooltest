## 0. 定位与前置培训

来源：A01。

**定位：**面向 BG 各业务部门的校招生 AI 实战培养统一规范，确保各部门在课题设计、过程管理、考核评价上对齐标准，同时保留业务特色的定制空间。

**前期培训（必修）：**校招生入职后至少已完成 AI 基础认知、Skill 开发、Vibe Coding 培训。本框架定位为进入部门后的落地实战，课题设计默认学员具备上述前置知识。

**前期培训（选修、可扩展）：**可结合自身能力扩展运用 Harness 工程（Agent = Model + Harness、多 Agent 编排）、知识管理（CLAUDE.md / Rules / Memory 体系）等高阶模块。必修模块为主体，选修模块作为加分亮点，而非准入门槛。

### 2.2 选题必须满足的条件

来源：A02，第 5 行详细内容在截图底部被截断。

| 条件 | 判定标准 | 不满足的反例 |
|---|---|---|
| 真实性 | 解决部门实际面临的工程问题，非凭空构造 | 用 AI 写贪吃蛇游戏，与业务无关 |
| 可交付 | 明确产出物定义：代码、脚本、文档或报告；30 天内可完成 | 用 AI 重构整个 Framework 层，粒度太大 |
| 可度量 | 能以数据进行前后对比或人工与 AI 对比 | 只提出“提升代码质量”，没有量化锚点 |
| 可复用 | 产出可被团队其他成员使用或集成到工作流 | 一次性脚本，用完即弃 |
| AI 深度 | 可见文字为“课题利用 AI 的能力超出纯代码补全”，后续涉及 Skill 开发 / Vibe Coding 的文字未完整展示 | 可见反例涉及“用 Copilot 写一个工具类”和“只用 IDE 补全”，完整行未展示 |

MVP 为最小可用版本（Minimum Viable Product）。原文时间、阶段和章节引用疑点见第 11 节。

### 3.2 Skills Creator 整改流程

来源：A04。原文小节标题为“Skills Creator 整改流程（S3 关键动作）”，其中 S3 与上表阶段编号不一致。

1. 学员完成初版 Skill。
2. 通过 Skills Creator 进行自动化整改，检查项包括：description 触发精度、正反约束、CRITICAL 标记、脚本黑盒化、自由度设定。
3. 根据反馈修改至通过。
4. 提交导师 review，附 Skills Creator 整改记录。
5. 导师评价 Skill 质量和整改效果。

提交的 Skill 须附整改通过记录。导师重点关注：

- 是否经过 Skills Creator 整改。
- 整改后是否解决了工具指出的问题。
- 是否仍有工具未能自动检测、但导师认为应改进的问题。

**延期处理原文口径：**确因合理原因无法按时完成，须在 S2 结束前确认；最长延期至第 6 周；延期课题考核总分上限扣减 1 分。

整理说明：会议纪要另有“自主搭建初版、禁止直接使用工具生成初版”的表述。截图没有完整重述该限制，不能据此推定限制已取消。初版允许的辅助范围待确认。

### 4.2 三项必交材料

来源：A05—A06。

| 材料 | 内容要求 | 评审重点 |
|---|---|---|
| 可运行交付物 | 源码、脚本或 Skill 包，含 README 和运行说明；可现场运行或演示录屏 | 真实可用、代码可读性、错误处理、脚本黑盒化原则，先查看 `--help` |
| 测试用例与验证数据 | 至少 5 条正向 case＋2 条负面控制 case；参考 Skill 评测的 4 类测试集方法 | 测试覆盖度、负面控制合理性、验证数据可复现 |
| 结题报告 | 问题背景 → 技术方案 → AI 运用方式 → 效果对比数据 → 经验总结 | 逻辑完整性、数据可信度、AI 运用的深度和合理性、整改是否到位 |

3. Skills Creator 检查发现的问题及整改情况。

### 5.2 中期检查评分

来源：A06—A07。原文标注“参考线，不计入总分”。

| 检查项 | 通过线 | 说明 |
|---|---|---|
| 核心功能可运行 | MVP 至少跑通 1 个端到端用例 | 允许 UI 粗糙、错误处理不完善 |
