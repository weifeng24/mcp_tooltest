## 2. 项目定位

**面向车载 MCP 服务的可用性评测与回归验证工具。** 围绕真实车端工具集回答两个问题：

1. 工具接口是否可用、参数约束是否清晰、错误是否可诊断（L1）。
2. 大模型能否根据自然语言任务正确选择工具并填对参数（L2）。

“工具是否好用”转化为可度量指标：工具枚举完整性、调用成功率、参数校验行为、错误可诊断性、模型选工具/填参准确率、任务完成率、单次任务耗时与开销。

## 4. 范围

### 4.1 首版范围（已确认）

- 被测服务：优先从候选中选择一小组可核验、可恢复的真实工具；不宣称已覆盖全部8个服务。
- L1 目标：工具定义、单工具调用、负面/边界行为与必要回读。当前设备适配为 `--toolscall`；发现/资源动作没有已验证采集入口，明确保留 blocked。
- L2 扩展目标：模型经自然语言任务选工具、填参并执行，争取第二模型对比；现有证据仅为历史 DeepSeek＋mock 冒烟，Kimi 实际产品协议待核实。
- 灵活配置的体现：被测工具集、模型、任务集、判定规则全部配置化（JSON）；模型一键切换并保留对比证据。
- 全程离线可开发：录制回放驱动；真机数据为最终结论依据。

### 4.2 首版不做（已确认）

- IDE 直连车机的 L3 评测暂缓。这是用户确认的首版取舍，仍与申报表的 IDE 目标存在差距，需要导师确认接受方式；模型配置不能替代客户端配置及真实评测。
- 四种 IDE 的逐一适配；云端 MQTT 链路评测；多车型树并行评测（以一棵树为准，候选 Ark 树）。
- 可选加分项（默认不做）：将评测工具本身封装为标准 MCP server 供 IDE 挂载演示。

## 5. 验收标准

1. 真机实测：L1 用例（≥5 正向＋2 负面控制）在车机真实执行，证据（请求/响应/日志）完整可追溯。
2. L2 扩展验收：若纳入最终范围，使用相同任务与判据验证模型选择、参数、真实执行和最终结果；第二模型不可用时保留未执行及范围变更依据，不宣称双模型完成。
3. 可复现：第三方按 README 能以回放模式复现报告；真机模式步骤明确。
4. 过程合规：≥5 次规范提交；Skill 附 Creator 整改记录；中期自评按时完成。
5. 答辩：15 分钟汇报（按部门最终口径调整）＋演示（录屏保底）。
