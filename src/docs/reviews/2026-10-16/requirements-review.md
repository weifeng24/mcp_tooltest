### A01 · P1：首版范围已获用户确认，但与申报表的 IDE 要求仍有差距

依据：`proposal.md:16,62-70`、`memory/DECISIONS.md:120-124`。承认 D013 的首版缩减决定，不擅自改回全客户端适配；但工具/模型/任务配置化不能证明 IDE 配置能力，使用某个 IDE 写代码也不是评测该客户端。

建议向导师提交明确范围差异：首版已实现/拟实现什么、哪个 IDE 能力暂缓、后续如何补验收。不要求四种产品全做，也不把用户确认等同于公司需求豁免。将评测器本身暴露为 MCP Server 与“在真实客户端评测被测工具”仍是不同成果，需各自定义验收。

### A02 · P1：业务工具与预期判据仍未冻结，当前用例覆盖少于说明书

依据：`tests/cases/README.md:3,9-13,34-42`，各 JSON 用例，`configs/servers/ark_mcp_service.json`。

- `HvacService.setTemp/getTemp` 及 16—30 示例来自协议手册，尚未证明它们就是所选 Ark 设备实际提供的接口；服务归属仍写 `auto`，运行时没有解析器。
- P01 声称“完整枚举、合法 Schema、关键工具存在”，实际仅检查列表非空、inputSchema 为字典、名称含点；不查 outputSchema，不查完整集合。
- P02 没有执行承诺的 getTemp 回读。P03 仅设为 16；重复同一用例不会覆盖 30。P04 仅调用单个工具，未验证多服务不串扰。
- P05 仅断言 tools/resources/content 任一非空，不证明目标资源存在、读取结构正确或完成先枚举后读取。N01/N02 将任意 error 视为预期错误，连“目标服务不存在”也可能通过。
- 不将“以实测为准修正预期”解释为事后把缺陷改成期望。应冻结业务契约、记录事实差异，再由预期结果确认人决定规范是否变更。

建议上机前从代码及负责人处确认一小组确定可用、可恢复状态的工具，建立 `server/version/tool/inputSchema/outputSchema/expected/restore` 清单，并让断言逐项对应预期。框架未完整定义负面控制分类，不能武断要求所有负面测试都必须是模型不调用；但其判据必须排除基础设施失败和错误服务等干扰。

### A03 · P1：量化目标没有完整的实验与指标实现

依据：`design.md:69-86`、`proposal.md:43,75`、`report.py:20-66`、`model_loop.py:119-120,200-216`。

目前报告统计的是断言通过率；没有独立的参数语义正确率、执行成功率、任务完成率、完整轮数和全程用量。前后对比被设计降为“时间允许”，而框架明确要求效果对比数据。建议选定至少一组固定任务和可控变量，冻结比较协议；不必追求提升，但必须保留基线、改进/另一配置、失败与缺失数据。单次合成 7/7 与双模型各一条任务不能推导稳定性或模型总体优劣。

### A04 · P1：Skill 初版可见，整改通过及对照结论尚不充分

依据：`skills-creator/fix-log.md:9-30`、`tasks/todo.md:38`、`skills/mcp-eval/evals/evals.json`。

- fix-log 写 3＋1 场景，但 evals.json 只有 3 条，未见逐次输出、grading、benchmark 或反馈文件。
- 先前对话里的“无 Skill”代理实际读取/引用过 `skills/mcp-eval/` 中脚本及参考材料；不能作为干净的无 Skill 对照。多个执行同时写 `replay-smoke` 同一目录，产物不隔离。
- “更快、无需探索”的增量价值没有时长/步骤等量化证据，应保留为待验证假设。
- `fix-log` 仍列完整检查待补，却勾选 T09 完成；缺少对框架列出的 CRITICAL、自由度设定、脚本黑盒化（先 --help）等逐项结果。`check_env.sh` 没有 --help 分支。

建议拆成“初版完成”和“整改验证待完成”，用隔离输出、明确基线可见文件和正反触发用例补齐证据。CLI 不是框架写明的唯一检查方式，是否以何种工具/版本满足检查应与导师对齐；不以工具不可用为由直接宣称整改通过。用户允许 Vibe Coding，但 Skill 初版是否有额外独立搭建约束仍按 D012 保留待确认。

### A05 · P1：完成状态超出实际证据，影响后续排期与答辩

## 4. 上机契约核对：可以先离线解决的事实

读取的是 `/data/AIOS_Ark_2026-dev/AIRuntime/MCPServices/Linux`，未修改该目录。

1. `app/test/TestConfig.cpp:111-137`：Android 默认配置 `/system/etc/test_config_ark.json`，与评测器写入路径不同。
2. `app/test/client/test_mcp_interface.cpp:147-175`：`--mcp <服务>` 的路径使用 `specific_services`；找不到服务配置时只列工具/资源，不执行生成器放在 `mcp_interface` 的指定调用。
3. 同文件 `:189-220`：`--mcp all` 运行配置内各 MCP 服务的测试，包含工具调用。它不是“只读取完整工具目录”的命令，应避免用采集之名意外执行既有状态修改。
4. `app/test/TestCommon.cpp:15-103`：ToolsList 正常路径只输出摘要/部分名称，完整 JSON 打印被注释。不能把该日志直接当工具 Schema 文件。
5. `app/src/main.cpp:161-166`、`app/test/client/test_toolscall.cpp:127-152`：基线源码已有直接 `--toolscall` 入口，是更小单工具执行适配的候选。设备二进制是否对应此源码仍需核实，不能据源码存在就认定真机可用。

## 5. 为什么 75 项测试没有拦住这些问题

- `test_channels.py:31-41,95-101` 的 FakeRunner 不检查生成配置是否被车端消费，只要收到第二次请求就返回预设成功。
- `test_model_loop.py:110-119` 在验证超轮时把断言上限改小到 2，避开了“硬上限 3、用例上限也 3、无最终答案仍通过”的情况。
- `test_runner.py:36-56` 以全通过的合成数据验证全通过输出，未覆盖中断、缺密钥、错参数、错误响应关联等关键反例；还把结果写回固定项目目录。
- `test_report.py:32-47` 只提供已存在的记录，无法证明缺失计划项仍在分母中；表格测试只查文字，不检查列数。

本轮保留这些测试的有效价值，但把结论限定为“已覆盖路径通过”。新增反例表明需增加独立车端契约样本、已知真值判定测试及异常批次测试，不能只增加类似成功样例的数量。

## 6. 整改顺序与验收门槛

### G1：上机前先解决可离线复现的阻塞

1. R01/R02/R08：固定实际客户端入口、配置消费、工具/参数/响应关联及完整发现格式；只选确认过的一小组工具。
2. R03/R04/R05/R10：禁止错误参数、缺失证据、模型失败和未完成任务出现假通过；超时后不再下发调用。
3. R06/R07/R09：证据不可覆盖、批次中断不丢计划项、回放身份与顺序可追溯；完整保存原始事件。

验收：相关反例变为正确行为；原测试继续通过；设备 dry-run 报告准确列明“已核验/仍待设备验证”，不显示笼统全就绪。

### G2：10-19/20 真机窗口

先核对设备二进制、工具目录及最低可用链路，再分批采集 5＋2。先采集原状态并安排恢复，按真实请求/响应判定；失败或受阻照实保存。L2 基于同一组真实工具定义执行，API 不可用时保留未执行项；第二模型未验证前不宣称双模型完成。

### G3：10-28 交付前

对齐 A01 范围差异；补齐真实工具集、量化对比和结题报告；完成可追溯 Skill 检查及整改；更新中期状态，验证独立运行，准备现场演示与录屏。评审用原始证据优先于展示百分比。

工时需要在车端入口确定后重新估计，当前不能承诺剩余整改都能压入每日 2 小时。代码模板自动给出的按问题数工时不作为本项目排期依据。
