# MCP工具评测结题报告（阶段草稿）

更新：2026-10-23。当前完成离线原型、可靠性整改、5正向＋2负面Skill行为验证，以及本地阶段展示与演示素材，尚未结题。本文仅引用已有证据；真实业务效果、自动触发及正式验收仍未完成。

## 1. 问题背景与目标

课题来源为“mcp工具 模型测试工具”，目标是评测工具是否好用并支持灵活配置模型及IDE/客户端。被测候选为公司车载`mcp_service`；预期交付MCP工具集、评测工具、评测报告，另按用户确认交付一个评测流程Skill。

本项目针对工具定义核对、调用结果判定和评测证据复现建设评测原型。被测服务依赖车端环境，开发机通过adb访问，设备使用机会有限，因此采用离线开发、集中真机采集、录制回放复现的方式。实际工具集和业务基线仍待设备确认。

首版接口级L1为必达，模型级L2尽量触达；真实客户端L3暂缓是用户确认的范围取舍，仍需导师接受与原申报目标的差异。完整需求见[proposal.md](../proposal.md)。

## 2. 技术方案

评测器使用Python和JSON配置，包含server/model/case/run四类输入。运行前校验引用和工具定义，冻结manifest中的任务、模型和重复次数，再通过device或replay通道执行。

- device：按已核对源码生成`--toolscall`单工具命令，关联唯一响应并保存完整输出；真实二进制仍需核验。
- replay：按请求顺序消费录制，缺失样本保留无法判断，不复制末次成功响应填补。
- judge：区分执行状态和业务判定，输出pass/fail/unassessed；错误响应不能仅凭局部字段判成功，后置读取需核对身份与结果。
- report：分母来自固定计划，按来源及模型分组；批次独立，报告可由冻结输入与结果重建。
- L2：模型自主选择工具，参数经过Schema校验，执行结果回填模型；独立回读不向模型暴露标准答案。
- 检查点：在调用边界保存部分记录，受控异常或中断时保留已经完成的调用；未开始任务使用not_run。

`capture-catalog`读取已有注册定义文件，可供工具目录整理和模型输入准备，但不等于实时工具发现或资源值读取。设计详情见[design.md](design.md)。

## 3. AI运用与培训衔接

### 3.1 开发方式

采用自然语言需求梳理、AI辅助实现、针对性评审和回归验证的迭代方式。评审中发现“现有测试通过但特定错误仍判成功”，因此把可复现问题写成先失败、修复后通过的测试，并保留审查与整改记录。

AI生成或修改的代码必须由独立输入、可重复测试及原始证据校验，不能以模型解释或测试数量替代真实效果。用户已确认允许Vibe Coding；Skill初版独立搭建的特殊要求仍需按公司口径确认。

### 3.2 Skill交互设计

评测Skill采用Tool Wrapper模式，封装现有命令行流程。元数据用于选择任务，主体规定操作顺序，按需加载报告与排错参考材料，体现渐进加载。

命令、目录、来源和指标计算使用低自由度；原因解释采用中等自由度，要求区分证据与假设。脚本先查看`--help`再按黑盒调用；使用CRITICAL规则强调证据完整性和合成数据边界。

这与Prompt设计、Bad Case→整改→回归、Skill约束与自由度、Vibe Coding过程留痕相衔接。A/B/C/D等培训分类尚缺完整定义；本地资料未找到原文，框架所列cookbook入口本轮读取失败，本文不自行归类。最小待补素材见[培训与业务依据表](training-and-business-inputs.md)。

## 7. 经验与限制

1. 数据来源必须随结果保存；device标签或文件存在不足以证明真实能力。
2. 判定器本身也需反例测试，错误标志、缺失证据、JSON类型和数值语义都会影响结论。
3. 中断后“未完成”不等于“未执行”，须保留已经完成的调用并核对远端状态。
4. 回放可降低稀缺设备条件下的开发成本，但不能替代首次真实采集或模拟任意状态变化。
5. 当前自动化尚不能证明真实工具好用、模型对比优势或IDE适配；提交前需补齐这些范围内的证据及正式接受记录。
