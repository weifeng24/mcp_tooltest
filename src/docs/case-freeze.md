## 2. 代表性任务候选

当前开发模板的Hvac名称、16—30范围和Voice返回字段均未绑定真实设备。下表仅规定任务意图，实际名称、范围和字段必须由采集结果决定。

| 槽位 | 任务意图 | 对应开发模板 | 正式冻结所需证据 |
|---|---|---|---|
| 正向1 | 正常范围内设置一项可恢复状态，独立回读 | P02 | 完整工具名、正常参数、成功字段、回读工具与目标值、原值及恢复方法 |
| 正向2 | 规范下界值，验证接受及回读 | P03 | 真实Schema/业务规范下界，不能直接套用16 |
| 正向3 | 规范上界值，验证接受及回读 | P06 | 真实Schema/业务规范上界，不能直接套用30 |
| 正向4 | 第二项代表性工具的合法调用 | P04 | 真实服务与工具定义、参数、业务判据及副作用恢复 |
| 正向5候选 | 独立只读状态查询，校验类型、单位和值的一致性 | 拟新增P07，尚未建立执行JSON | 实际读取工具、可独立确认的状态/规范；不能以另一任务的附带回读重复计数 |
| 负面1 | 对已确认服务请求不存在的方法 | N01 | 可验证的服务存在性、未知方法错误码及原因；服务离线不算预期错误 |
| 负面2 | 在规范外输入非法参数 | N02 | 真实范围、拒绝契约、错误码/原因及状态核查方法 |

至少5正向＋2负面以独立case_id和真实证据计数。上表未冻结前不是“已有5＋2可执行”。若某种工具没有上下界，按实际契约重新设计任务并记录理由，不虚构边界。

**实时发现单独保留：**用户确认的L1目标包含真实tools/list。P01目前blocked；catalog文件采集不能替代它。补齐接口，或取得导师接受范围调整的明确记录后才能关闭此项。P05资源读取同样保留未支持状态，不删除原批次分母。

## 3. 每条用例的冻结字段

在编辑器打开实际用例JSON，按[用例说明](../tests/cases/README.md)填写以下信息；执行前由确认人核对。

| 字段 | 应记录内容 |
|---|---|
| 标识与分类 | case_id、positive/negative、评测层次及任务来源 |
| 工具身份 | 完整服务/工具名，catalog原名及别名，设备验证结果 |
| 输入 | 完整JSON参数、输入Schema及其版本/文件哈希 |
| 预期 | 来自规范的成功/错误条件，具体字段路径、类型和值 |
| 时限 | 用例timeout_seconds和批次总任务上限；以较小值执行 |
| 后置检查 | 读取工具、参数、预期路径和值；读取本身必须成功 |
| 恢复 | 原状态的读取证据、恢复调用、恢复后的回读判据 |
| 确认 | 确认人、日期、规范路径/章节、无法自动判断的部分 |

`expected_source`记录确认依据；可将确认人、日期、恢复说明保存在用例`notes`和本表。不要新增当前配置校验器不支持的JSON字段。

## 4. 执行与异常记录

具体命令、执行目录和设备核验见[device-readiness.md](device-readiness.md)及[catalog-capture.md](catalog-capture.md)。采用“单条读取→单条可恢复设置→已冻结批次”的顺序。

每批保存manifest、results、artifacts、summary、报告及恢复记录。`executed`是尝试项数，不是成功调用数；检查点中的`execution_in_progress`或中断记录表示结果尚未确定。

中断后先保留现场日志和已有检查点，再核对实际设备状态。不要仅因报告显示unassessed就重发设置操作。已完整判定的条目可保留原结论；未完成项与尚未开始项必须区分。

| 现场记录项 | 填写内容 |
|---|---|
| 批次路径、开始/结束时间 | 尚未执行 |
| 原状态及依据 | 尚未采集 |
| 计划/尝试/通过/失败/无法判断数 | 尚未执行 |
| 失败或中断条目与原始证据 | 尚未执行 |
| 恢复动作、恢复结果及确认人 | 尚未执行 |
| 是否需要第二次用机、具体缺口 | 首次用机安排尚未确认 |

## 5. 对比实验

先选择唯一改变因素，再冻结两组相同任务、工具集合、时限及判定。可比较同一模型下工具说明改进前后；第二模型真实可用时也可进行模型对比。不同因素同时改变时不能将差异归因为单一因素。

保留每组样本数、计划内通过率、判定覆盖率、失败类型、分组耗时、可获得的逐轮用量及未知项。当前没有真实对比批次，不预填改善比例。模型执行器使用模拟工具时，数据只能解释该模拟条件下的表现。
