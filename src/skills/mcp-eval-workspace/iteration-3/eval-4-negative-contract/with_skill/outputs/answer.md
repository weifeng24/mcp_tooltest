# 场景4：越界参数却返回成功

执行性质：主上下文读取当前Skill后的题设分析，非独立子代理运行。本场景没有执行真实请求或状态回读。

**在题设确认的16—30度规范要求拒绝越界参数、且40度请求与成功响应的真实关联证据完整时，N02应判 `fail`。** 负面控制用例预期服务拒绝40度；返回成功不符合该预期，不能因为调用成功就将负面测试判为通过。〔1〕〔2〕

保留设备/服务二进制与工具定义版本、冻结用例和错误判据、请求参数40、原始请求ID、完整原始响应及日志，注明批次、case、模型与重复序号（实际存在时）。后续还应按已确认的恢复条件回读状态，区分实际接受40、截断到30或未生效；在未取得回读证据前，这三种情况都只是待验证假设。本场景未回读，因此不能写“已经接受40”或“已经截断到30”。只要冻结契约要求拒绝，回读结果用于诊断，不将成功响应倒改为符合拒绝预期。〔1〕〔3〕

本地 `tests/cases/l1/N02_param_out_of_range.json` 确实使用 `temperature=40`、`error_expected` 和 `-32602`/温度越界消息模式，但文件也明确这些是开发判据，正式运行前须由真实接口契约确认。本地模板本身不能证明真实服务必须使用 `-32602`；题设已确认的真实规范和冻结判据才是该真实场景的判定依据。〔2〕

保留N02在原manifest计划分母N中，并计入失败F，不删除该条；题设没有完整计划，不能臆造总数。禁止看到结果后把预期从“拒绝”改成“成功”；如果真实规范后来正式改为截断，应另行确认版本并用于新批次，原批次保留原冻结预期和判定。〔1〕

以上是条件成立时的判定建议，不是本轮真机测试、自动触发验证或导师验收结论。
