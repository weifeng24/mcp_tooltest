# 报告解读契约

1. 按 CLI 输出读取实际批次目录；新批次使用唯一 ID，不覆盖旧数据。
2. 先查 manifest 的固定计划、工具/用例/模型配置、源码哈希，再查每项结果与 artifacts。
3. 同时检查 `channel` 和 `source_type`。synthetic 是人为样本；recorded_device 是历史设备记录的回放，不证明当前设备表现；live_device 也需要对应请求、响应、日志及版本证据。
4. `pass` 要求全部断言及后置条件通过；`fail` 表示完整证据确认不符合预期；`unassessed` 表示未执行、基础设施/配置错误或证据不足。已观察到禁止调用的违规，不因后续 API 失败而撤销。
5. 计划内通过率 P/N、判定覆盖率 (P+F)/N 的 N 来自 manifest。缺失项不能删除，分母为零时不适用。
6. 模型轮数是模型请求次数，工具调用数另计；逐轮 usage 未提供的字段保持未知，不把最后一轮当总量。
7. 负面用例必须匹配预先定义的错误类型/原因，其他错误不能算通过。业务预期须评测前冻结；不要根据结果倒改预期。
8. 引用结果给出 run_id、case/model/repeat、分母及证据。API＋模拟工具只证明模型接入链路；不可据此宣称真机或 IDE 通过。

人工复核没有完成时保持 unassessed；需保存复核人、时间、依据，不能直接编辑 summary 掩盖原始判定。
