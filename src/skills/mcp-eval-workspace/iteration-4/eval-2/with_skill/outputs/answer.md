# 场景 2：历史“未调用工具”判定复核

## 结论

**不能证明模型正确地没有使用工具。** 这条记录只能证明保存的工具调用列表为空，同时执行报错、轨迹不完整；它不足以证明模型完成了任务并正确决定不调用工具。历史 `verdict=pass` 缺乏证据支持，应在本次解释中将模型行为标为 **`unassessed`（无法判断）**，保留执行错误及原始判定，不修改历史证据。

## 字段证据

| 用户提供的字段 | 能支持的判断 | 不能据此推断的内容 |
|---|---|---|
| `execution_status=error` | 本次执行记录为错误状态 | 模型已正常完成任务 |
| `error_category=provider_error` | 记录将错误归为模型提供方／接入错误 | 具体是鉴权、网络、限流或其他原因；也不能直接归咎于模型能力或被测工具 |
| `tool_calls=[]` | 该记录未保存工具调用条目 | 实际全过程没有调用，或模型有意识地正确选择了不调用 |
| `trace_complete=false` | 调用轨迹不完整，存在证据缺口 | 用空列表排除未记录的调用 |
| `verdict=pass` | 历史评测器曾输出通过标签 | 标签本身可以替代完整的执行证据 |

提供方请求失败可能导致没有可评估的模型输出；轨迹缺失也可能造成调用未被保留。这些是解释空列表的可能机制，当前字段不能确定具体发生了哪一种。不能把执行链路错误当成模型正确克制调用的表现，也不能仅凭该错误认定模型选择工具的能力失败。

按 `references/report-guide.md`，`pass` 需要全部断言及后置条件通过，`fail` 需要完整证据确认不符合预期，基础设施错误或证据不足应为 `unassessed`。若另有证据明确显示禁止的调用已发生，该违规不能因后续 API 错误而撤销；本题未提供此类证据。

- 分析对象：用户在任务中给出的 **1 条历史记录字段摘录**；未提供原始批次路径、`run_id`、用例／模型／重复编号。
- 本条可获证据支持的模型行为判定：通过 **0**、失败 **0**、无法判断 **1**。这不是重建后的批次统计，也没有改写原始 `pass`。
- 批次计划数、未执行项及其数量未知。未读取该批次的 `manifest.json`、`results.jsonl`、`summary.json` 或原始响应，不能计算批次通过率；无法判断项不能从计划分母中删除。
- 已读取 `skills/mcp-eval/SKILL.md` 及其报告规则、故障处理参考。项目索引和交接文件仅按项目协作要求读取，不作为本条记录的原始证据。

## 支持“正确不调用”还需要的证据

需要同一批次冻结的用例预期及工具配置，确认该场景确实应当不调用工具；还需要成功完成的模型交互、最终响应、覆盖全过程的完整调用轨迹，以及全部相关断言和后置条件通过的依据。最终响应也应符合用例要求，仅仅没有工具调用仍不充分。

如后续复核，应以该批次的 `manifest.json`、`results.jsonl`、`summary.json` 及关联原始请求、响应和轨迹为依据，定位错误与历史误判原因。当前足以得出“证据不能支持通过”，尚不足以确定评测器具体缺陷或提供方错误根因。
