# N02 越界参数返回成功：判定与处理

## 1. 结论

**按本组冻结规范，N02 应判为 `fail`，原因为“预期错误未出现”。** 这是接口级（L1）的负面用例：传入越界参数后，符合预期的行为是拒绝请求并返回指定错误；返回成功不代表用例通过。

本次输入明确标记为 `synthetic`（合成数据），用途是离线分析规范与响应冲突。因此该结论只适用于给定情景，不能写成已发现或复现真实车机缺陷。

| 判定对象 | 本次结果 | 依据与边界 |
|---|---|---|
| N02 的冻结错误断言 | `fail` | 请求温度 40 超过上限 30，但响应没有预期错误 |
| 本机离线判定核验 | 已完成，得到上述失败结果 | 直接调用本组判定器，未发起工具调用 |
| 设备实际温度及其他状态 | 未知，无法评估 | `independent_state_readback=null` |
| 真机缺陷及具体根因 | 未确认 | 仅有合成夹具，没有真实服务执行证据 |
| 恢复是否完成 | 未执行、未验证 | `recovery_method="未在真实设备确认"` |

## 2. 冻结事实与判定依据

主依据为交付根目录下的 `fixtures/anomaly.json`：

- 工具版本：`fixture-v1`；规范版本：`frozen-fixture-2026-10-23`。
- 允许温度范围：`[16, 30]`；被测工具：`HvacService.setTemp`。
- N02 请求参数：`{"temperature":40}`，请求方法为 `tools/call`。
- 请求与响应的 `id` 都为 `1`；请求中的工具名、参数与冻结用例一致。
- 冻结断言：`error_expected`，错误码须属于 `[-32602]`，错误信息须匹配 `(?i)temperature.*(out of range|maximum|range)`。
- 给定响应为：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "isError": false,
    "success": true
  }
}
```

响应既没有顶层 `error`，也没有工具结果中的错误标记。`success=true` 是响应声称的执行结果；用例是否通过仍要与冻结预期比较。此处不是“返回了其他错误码”，而是根本没有出现预期错误。

本组 `tests/cases/l1/N02_param_out_of_range.json` 与夹具内的 `case` 完全一致。源码依据为：

- `src/mcp_eval/judge.py:174–175`：`error_expected` 进入专用错误判定。
- `src/mcp_eval/judge.py:229–246`：没有顶层错误，且 `result.isError` 不为 `true` 时，返回失败及“预期错误未出现”；存在错误时还须同时核对错误码、错误原因。
- `src/mcp_eval/judge.py:159–160`：断言明确失败时，总判定为 `fail`。
- `src/mcp_eval/judge.py:113–118`：实际执行或证据不完整时另有 `unassessed`（无法评估）分支。本次离线核验将给定请求与响应作为完整的合成输入，不据此宣称真机跟踪完整。

缺少状态回读不会消除已明确观察到的响应契约冲突，也不能把当前 N02 改为通过。它限制的是对实际设备状态及影响的判断：不能断言温度已设为 40、被自动限制到 30、保持原值或已经恢复。

## 3. 应如何处理

### 3.1 固定失败结论并保留证据

1. 将本次情景记录为 `N02 / synthetic / fail / 预期错误未出现`，保留在负面用例统计中；不计入真实设备通过率或缺陷数量。
2. 保留原始夹具、冻结规范及用例、完整请求和响应、版本标识、判定理由、文件哈希。不得删除失败项，或用后来运行的数据覆盖原结果。
3. 不因响应声称成功而删除 `error_expected`、扩大允许范围、改传合法温度，或将当前预期改成成功。此类做法会改变被检验的问题，不能修复当前失败。

本次已保存离线判定的原始标准输出、标准错误，以及七个已读输入/源码文件的运行前后 SHA-256 哈希。SHA-256 用于核对文件内容是否变化，不代表接口行为已通过。

### 3.2 暂停 N02 的真实重试，先明确状态与恢复条件

本轮没有连接或操作设备。以下为该情景进入真实验证后的处理条件，尚未执行：

- 若在真实设备观察到同类异常，暂停 N02 及依赖该温度状态的后续写操作，保留当前失败证据，不连续重发 40 或尝试更大数值。
- 需要通过已确认的独立只读途径获取当前状态，并与测试前状态比较；不能用设置接口的成功回执代替状态回读。
- 恢复方法和测试前基线尚未确认时，将恢复状态记为“未验证”，将新的主动测试记为阻塞。不得自行猜测默认温度、恢复命令或宣称已恢复。
- 后续需由接口/设备负责人明确读取与恢复方法，并在恢复后取得独立回读证据，才具备继续主动验证的条件。这不改变本次已记录的 `fail`。

### 3.3 核对规范与实现，区分候选原因

夹具的 `expected_source` 已注明：错误码和信息属于开发判据，正式运行前须由接口契约确认，禁止事后按实测改判为通过。因此：

1. **本情景继续按冻结规则判失败。** 不能用“真实契约还待确认”抹去给定规范与响应之间的矛盾。
2. **真实缺陷定性前核对正式契约。** 确认实际部署版本对应的工具定义、参数范围、越界处理方式及错误表达，并确认日志中的请求、响应属于同一次调用。当前 `fixture-v1` 不是已核实的设备二进制版本。
3. **将原因保留为待排查假设。** 可能是服务端未落实范围校验、工具定义与实现版本不一致、参数/路由处理异常，或响应层错误地报告成功。夹具不足以在这些原因中作唯一归因。
4. 若正式契约确认越界必须拒绝，整改应保证在产生设备副作用之前完成校验，并返回契约约定的错误。仅在评测器或客户端提前拦截参数，不能证明服务端通过了 N02。
5. 若权威契约实际允许另一范围或规定自动限幅，应先由负责人明确规范差异，形成新版本规范、用例与变更原因，再开展新批次验证。旧版本 N02 的失败及证据仍保留；不能为迁就本次成功响应而回写旧预期。

### 3.4 复测与关闭条件

本轮没有修改产品或执行真实复测。后续针对 N02 的关闭条件为：

- 在已确认版本、状态读取和恢复条件下，仍使用该版本冻结的越界请求验证服务端行为。
- 对当前冻结断言，必须真正返回匹配的错误码和越界原因；通信失败、超时、无权限或无关错误不能替代正确拒绝。
- 真实验证另需独立证明未发生非预期状态改变，并在必要恢复后确认状态。该项是设备影响与恢复的验证要求，不冒充当前夹具已包含的后置断言。
- 保存新旧版本、批次、原始证据及复测结果；只有满足相应确认条件才关闭问题。本轮输出不代表已整改或已关闭。
