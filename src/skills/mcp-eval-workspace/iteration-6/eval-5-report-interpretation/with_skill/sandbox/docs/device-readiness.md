## 1. 当前可验证的命令契约

基线源码 `app/test/client/test_toolscall.cpp:117-131` 使用 `id=1` 构造单个 `tools/call`，并打印请求/响应；`app/src/main.cpp` 有 `--toolscall` 参数处理。开发机适配按此生成命令，使用 shell 引用保证 JSON 参数不被拆分，保存完整 stdout/stderr，只选择唯一匹配响应。

现有工具发现与资源读取没有独立、已验证的机器可读采集入口。`--mcp <服务>` 读取 `specific_services`，`--mcp all` 还可能执行已有的车窗/空调等配置调用；两者不能替代纯只读工具发现。当前对应评测条目明确为 `blocked/unsupported_action`。

## 2. 在公司现场先确认以下信息

操作位置：开发机 Ubuntu Bash，进入 README 所述交付根目录。车机通过 adb 连接。设备 root、服务重启能力由现场确认，不作为已验证事实。

### 设备身份

目标：防止发给错误设备。

```bash
adb devices
```

预期设备状态为 `device`。将目标行第一列填写到 `configs/servers/ark_mcp_service.json` 的 `device_serial`；`unauthorized` 表示尚未授权，`offline` 表示连接未就绪，应先处理连接，暂不运行批次。多台设备必须选择具体序列号。

### 二进制版本与命令

填写实际 `service_bin` 后生成清单：

```bash
PYTHONPATH=src .venv/bin/python -m mcp_eval checklist
```

清单会给出带实际序列号的只读命令。无参数调用 `mcp_service` 在当前源码中会显示用法并非零退出，此处需要人工检查是否出现 `--toolscall`，不是按退出码判接口成功。若找不到程序或参数不支持，记录设备实际路径、版本和输出，不推送未知二进制覆盖系统程序。

本地源码 commit 只证明开发依据，不能证明设备安装了对应产物。应记录设备版本及二进制来源；尚未取得时写“未确认”。

### 工具与用例契约

- 获取完整原始工具 JSON，保留设备/服务版本与采集方式。摘要日志不足以恢复 inputSchema。
- 选择一项实际可用的读取工具，先核对请求与响应；再选择可恢复状态的设置工具。
- 校准完整工具名、输入参数、返回字段、预期错误类型与状态回读。冻结后再做正式评测；实测偏离规范应记为发现，不能直接改预期以提高通过率。
- 确认状态修改前的原值和恢复步骤。执行异常、连接中断或超时时，远端状态可能未知，应先核对状态再决定是否重试。

## 3. 准备一次可解释的最小批次

1. 复制开发用例到已确认的任务集，保留确认来源和日期；不要直接把文档中的 Hvac 示例当作真实设备工具。
2. 用 `show-call` 检查将发出的工具名和 JSON 参数，不执行设备动作。
3. 对对应 run 配置执行 `--dry-run`，处理缺少的引用文件/密钥；预检不会验证设备实时连通性。
4. 使用填写后的设备配置运行一条 `tools_call` 用例，核对 `request_raw`、完整输出、响应 id、postconditions 和判定。
5. 若正常，再扩大到确认过的至少 5＋2 条任务；不支持的动作和未执行项留在分母中。
6. 根据原值恢复状态，保留操作记录及现场日志到本次返回的独立批次目录。

当前不能保证一次上机完成所有任务。若完整工具发现仍不可用，应先取得原始接口数据并明确阻塞，不能以合成结果替代。
